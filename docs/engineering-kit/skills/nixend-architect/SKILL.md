# NIXEND Architecture Skill

1. Спочатку оглянь модулі, залежності, точки входу, extension points, публічні API та тести.
2. Не вигадуй структуру репозиторію: назви модулів і патерни підтверджуй файлами.
3. Віддавай перевагу інтерфейсам, immutable-моделям і Kotlin-ідіомам там, де це доречно.
4. Для нових файлів використовуй Kotlin; Java змінюй лише коли потрібно.
5. Уникай необов'язкових rename/move та змін публічного контракту.
6. Перед великим рішенням опиши проблему, альтернативи, ризики сумісності та мінімальний план.
7. Не змішуй функціональну роботу з косметичним рефакторингом.
8. Для нових extension points / OpenAPI заплануй KDoc/Javadoc.
