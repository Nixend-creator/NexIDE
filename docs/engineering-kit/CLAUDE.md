# Claude Code — NIXEND IDE Project Instructions

Ти працюєш над IDE-аналогом IntelliJ IDEA. Дотримуйся `AGENTS.md` і `standards/INTELLIJ_PLATFORM_CODING_GUIDELINES_1.0.md`.

## Обов'язковий порядок роботи

1. Визнач контекст репозиторію: мову, модулі, наявні архітектурні рішення, правила збірки, тести й локальні conventions.
2. Для нових файлів використовуй Kotlin. Модифікуй наявний Java-код лише коли це потрібно для задачі або підтримання поточної Java-області.
3. Перед змінами сформулюй короткий план і межі змін. Не переробляй незв'язані ділянки.
4. Для нової функції або виправлення помилки додай відповідні тести.
5. Після змін виконай доступні цільові тести, збірку, форматування та інспекції. Не заявляй про успіх команд, які не запускав.
6. Перед завершенням переглянь diff: прибери незавершений код і TODO, перевір сумісність і конфігураційні файли.
7. Підсумуй змінені файли, рішення, перевірки та обмеження.

## Код-стиль

- Відступи: 2 пробіли, ніколи tabs.
- Максимальна довжина рядка: 140 символів.
- `else`, `catch`, `finally` — на новому рядку.
- Префікс `my` для instance-змінних; `our` для static/class-змінних.
- Кожен новий файл повинен містити copyright-заголовок Apache 2.0 та ім'я контриб'ютора.
- Використовуй `.editorconfig` і спільний code style проєкту.
- Перед комітом — Reformat Code (Ctrl+Alt+L), якщо доступно.
- Не допускай попереджень із shared Inspection Profile; не змішуй функціональні зміни з окремим косметичним прибиранням.

## Kotlin та IntelliJ Platform

- Kotlin — пріоритетна мова для нових файлів.
- Використовуй ідіоматичний Kotlin, null-safety, data/sealed classes та extension functions там, де це доречно.
- Віддавай перевагу immutable-об'єктам і програмуванню через інтерфейси.
- Позначай експериментальні API через `@ApiStatus.Experimental`.
- Для `catch (e: Throwable)` або `catch (e: Exception)` спочатку викликай `rethrowControlFlowException(e)`, потім логуй/обробляй помилку.
- Не перехоплюй `CancellationException` вручну.
- Для нових OpenAPI — Javadoc/KDoc з описом призначення та параметрів.
- Для Kotlin build scripts дотримуйся правил стандарту: `@JvmField` для internal data class fields; надавай перевагу `.put()` / `.get()` оператору `[]`; явні `HashMap` / `HashSet` / `LinkedHashMap` замість `mutableMapOf()` / `mutableSetOf()`.

## Межі

- Не вигадуй API, сигнатури, версії чи результати.
- Не змінюй або переміщуй символи без потреби: зворотна сумісність критична.
- Не змінюй `.idea/*`, `codeStyleSettings.xml` та інші налаштування IDE, якщо це не є частиною задачі.
- Один PR/patch — одна логічна зміна.
- Не включай випадкові rename/move.
- Якщо інструкції суперечать коду або стандарту, зупинись і поясни конфлікт, а не приховуй його.
