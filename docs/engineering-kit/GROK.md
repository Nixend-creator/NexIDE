# Grok — NIXEND IDE Project Instructions

Ти — інженерний агент проєкту IDE-аналога IntelliJ IDEA. Виконуй `AGENTS.md` та `standards/INTELLIJ_PLATFORM_CODING_GUIDELINES_1.0.md` як нормативні правила.

## Робочий протокол

1. Прочитай інструкції, стандарт і релевантні файли проєкту перед редагуванням.
2. Спочатку визнач наявні мову, структуру модулів, API, стиль, тести та build-конвенції. Не припускай, що репозиторій має типову структуру, доки не перевірив.
3. Нові файли пиши Kotlin; наявний Java змінюй, коли це необхідно.
4. Зроби мінімальний, сфокусований diff для однієї логічної зміни.
5. Для нової функції чи багфіксу додай тести та перевір регресії.
6. Запусти доступні тести, збірку, форматування та інспекції. Якщо не можеш виконати команду, явно познач її як невиконану.
7. Перевір diff, сумісність, copyright-заголовки, документацію та відсутність випадкового TODO.
8. У фінальній відповіді дай: що змінено, чому, які перевірки виконані, результати та що залишилося неперевіреним.

## Нормативні правила

- Kotlin у пріоритеті; Java — лише для необхідних змін існуючого Java-коду.
- Ідіоматичний Kotlin: null-safety, data classes, sealed classes, extension functions; immutable-об'єкти та інтерфейси за можливості.
- Відступи — 2 пробіли, tabs заборонені; рядок — до 140 символів.
- `else`, `catch`, `finally` починай з нового рядка.
- `my` — instance-змінні; `our` — static/class-змінні.
- Новий файл має містити Apache 2.0 copyright-заголовок та ім'я контриб'ютора.
- Дотримуйся `.editorconfig` і shared code style; перед комітом зроби Reformat Code (Ctrl+Alt+L), якщо інструмент доступний.
- Нуль попереджень у shared Inspection Profile. Не змішуй функціональний patch з окремим прибиранням попереджень.
- Нові OpenAPI мають Javadoc/KDoc з призначенням і параметрами.
- Для `catch (Throwable|Exception)` першим викликай `rethrowControlFlowException`; не перехоплюй `CancellationException` вручну.
- Не ламай зворотну сумісність; не роби rename/move без необхідності.
- Перед push переглянь зміни, видали незавершений код і TODO. Не додавай `.idea/*` та `codeStyleSettings.xml`, якщо це не частина виправлення.
- Будуй і тестуй проти останньої версії `intellij-community`, якщо середовище це дозволяє; якщо ні — вкажи обмеження.

## Заборони

- Не вигадуй API IntelliJ Platform, результати тестів, стан CI або сумісність.
- Не стверджуй, що тест пройшов, якщо він не запускався або не має підтвердженого результату.
- Не змінюй широку архітектуру заради локального багфіксу.
- Не замінюй правила цього проєкту загальними стилістичними уподобаннями.
